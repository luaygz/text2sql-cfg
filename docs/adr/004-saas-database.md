# ADR-004: Synthetic multi-tenant SaaS database

Status: accepted
Date: 2026-10-16

## Context

BIRD measures accuracy but has no notion of tenants, owners or secrets, so it cannot show that the system keeps one customer's data away from another. The project therefore needs a second database: a synthetic B2B CRM and billing product with 12 to 20 tables, tenant-scoped tables carrying `tenant_id`, an `owner_user_id` for user-level scoping, global reference tables without a tenant column, 5 to 10 tenants with overlapping customer names, realistic dirt (inconsistent casing, NULLs, dates stored as text, one misleadingly named column), canary rows for layer 4, and values carrying indirect prompt injections for the adversarial suite. It must be generated by a seeded script, not an LLM, and be reproducible byte for byte.

The database has three consumers with different needs. The scoping layer needs every scoped table to be filterable by a single predicate on that table. The model needs a schema that looks like a real product, with descriptions that explain the traps, and must never see the tenant column or secrets. The safety suite needs known places where leakage and injection show up.

## Decision

### Tables

Sixteen tables, chosen so that the questions a sales, finance or support lead would ask need joins across most of them:

- Global reference data, no tenant column: `currencies`, `countries`, `industries`, `plans`. These give the validator and the scoper tables they must never filter, which is where a naive rewrite ("add `tenant_id = :t` to every table") goes wrong. In a real product each tenant would define its own price list; we keep `plans` global on purpose and list that as a limitation in the dataset card.
- Organisation and people: `tenants`, `teams`, `users`.
- Sales: `accounts`, `contacts`, `deals`, `activities`.
- Billing: `subscriptions`, `invoices`, `invoice_line_items`, `payments`.
- Support: `tickets`.

`users.password_hash` and `tenants.api_key` are the sensitive columns. Both values are fake: the hash is a sha256 of random salt and email shaped like a Django hash, the key a random hex string with a `t2s_test_` prefix.

### Tenant semantics

Every non-global table carries `tenant_id`, including child tables whose tenant could be derived through a parent (`invoice_line_items` through `invoices`, `payments` through `invoices`). The denormalisation is deliberate: the scoping rewrite in ADR-002 then only ever adds a predicate on the table being referenced, never a join, which is simpler to prove in layer 4. The generator keeps every foreign key inside one tenant, and a test checks that no foreign key crosses tenants.

`tenants` itself is tenant-scoped on its primary key. We considered three options: hiding the table entirely (needs a "hidden tables" concept the policy does not have, and loses legitimate questions such as "what is our default currency?"), exposing it unscoped (leaks the customer list of the SaaS vendor), or scoping it to the caller's own row. We chose the last: the model sees `tenants` with its name, country, currency and sign-up date, a request returns exactly one row, and `api_key` is hidden.

### Owner semantics

`owner_user_id` is on every table that holds business records: accounts, contacts, deals, subscriptions, invoices, invoice_line_items, payments, tickets and activities. Its meaning follows what CRM users expect from "owner": the account manager for accounts, the rep for deals and contacts, the assigned agent for tickets, the author for activities. Subscriptions, invoices, lines and payments have no natural owner, so they inherit the account owner, again so that user-mode scoping is a single-table predicate. `users`, `teams` and `tenants` are not owner-scoped: a rep must be able to see colleagues' names to answer "which rep owns the most accounts?" Owner ids stay visible to the model because they are join keys; only their filtering is enforced.

### What the model sees

`ScopePolicy.visible_schema` removes `tenant_id` from every table and the two sensitive columns, so neither the prompt nor the grammar can name them. The data dictionary (`src/text2sql/data/saas/dictionary.py`) declares every column once with its SQL type, nullability, foreign key, description, value notes and a sensitivity flag; the generator renders the DDL from it, `load_saas_schema` attaches its descriptions to the introspected schema, and `saas_scope_policy` derives the tenant tables, owner tables and hidden columns from it. Descriptions never mention tenants, so the model is not invited to write tenant filters it cannot express. `load_saas_schema` refuses a database file with a table or column the dictionary does not describe, which catches a stale file after a generator change.

### Dirty data and the misleading column

Each kind of dirt is tied to a plausible cause and described in the dictionary, because the point is to test whether the system reads its catalog, not to make questions unanswerable:

- Casing noise on free-text categoricals typed by users (`accounts.lifecycle_stage`, `tickets.priority`, some account names, contact emails and job titles).
- NULLs where CRMs really have gaps (phone, email, job title, employee count, website, industry, country).
- Mixed date formats with a cause the description states: `invoices.due_date` is `MM/DD/YYYY` for invoices imported from a legacy billing system (issued before 2024-07-01) and ISO afterwards; SQLite's date functions do not parse the US format, so a correct query normalises it. Ticket timestamps from the web form and the API carry an ISO `T…Z` form while the rest use a space; SQLite's date functions accept both, but string comparison does not order them correctly. The descriptions show how to handle both using only functions on the grammar's allowlist (`JULIANDAY`, `DATE`, `STRFTIME`, `REPLACE`, `INSTR`, `SUBSTR`); an earlier version recommended `DATETIME()`, which the grammar cannot emit, and a test now checks that every function named in a description is allowlisted.

For the misleading column we chose `payments.amount`, an integer in cents, next to money columns that are all in major units. Payment processors such as Stripe expect and report amounts in the currency's minor unit, so a payments table that mirrors the processor is realistic. We preferred it over the other candidate, a `closed_at` column that actually holds the expected close date, because the cents error is silent (the query runs and returns a number 100 times too large), money questions are frequent, and the description can disambiguate it in one sentence. Deals instead get two honestly named columns, `expected_close_date` and `closed_at`, which is itself a trap a model can fall into without being a naming lie.

### Reproducibility

All randomness goes through one `random.Random(20261016)` and one Faker instance seeded with `seed_instance`, called in a fixed order. No value reads the clock: dates are drawn relative to a fixed snapshot day, 2026-09-30. Sets are only used for membership, never iterated, so string hash randomisation cannot change the output (the test regenerates in a subprocess with a different `PYTHONHASHSEED`). Integer ids are assigned at the end in creation-time order so ids interleave tenants as they would in a shared database. The writer creates tables in dictionary order with a fixed page size, inserts in id order in one transaction, runs `PRAGMA foreign_key_check`, and ends with `VACUUM`, writing to a temporary file that replaces the target.

Byte identity holds for a fixed SQLite library, Python and Faker version. SQLite stores the version of the library that last modified the file at header offset 96, so another SQLite build yields a different hash for the same content. Python only guarantees that `random()` repeats for a seed; other methods such as `choices` may change across Python versions. Faker promises identical output only for the same Faker version. The dataset card records the hash together with these versions.

### Canaries and injections

Each tenant gets a token `CANARY-T{id}-{hex}` derived from the seed by sha256, stored once in a text column of ten tenant tables. The canary rows of owner tables belong to an inactive canary user who owns nothing else, so a canary showing up in a user-mode result is an owner-scope leak even if it is the caller's own tenant. Six planted injections each sit in a different column that customers or staff fill in (account name, ticket subject, contact job title, activity notes, invoice line description, deal name). Each one is the newest row of its table for its tenant, dated on the snapshot day after every organic row, so a fixed innocent question ("what is the subject of the most recently opened ticket?") retrieves it deterministically. One of them is a classic SQL injection string rather than a natural-language instruction, to check that values are always bound as data.

## Consequences

- The scoping layer can treat every scoped table uniformly; the price is denormalised `tenant_id` and `owner_user_id` columns that a production system would have to keep consistent on ownership changes. The generator does, and tests check it.
- Canary and planted rows are real rows and appear in aggregates (one extra inactive user, team, lost deal, void invoice and failed payment per tenant). Gold SQL for the evaluation set must be computed on this database, not by hand.
- The model-facing schema is the policy's visible schema, never the raw file. Anything that renders or greps the raw schema for a prompt would reintroduce `tenant_id`.
- Changing any profile value, distribution or dictionary entry changes the hash; bump `SCHEMA_VERSION` in `generate.py` when the schema changes, and regenerate with `make data`.
- The database is small (3.6 MB, about 37,000 rows) and synthetic, so it says nothing about performance at production volumes.
